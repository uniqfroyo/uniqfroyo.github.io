Internationalization (i18n) and Localization (l10n) of UI Design

Supporting multiple languages is not the same thing as designing internationally — the difference shows up in the grid, not just the copy.

Internationalization (i18n) is the framework that makes a product adaptable in the first place. Localization (l10n) is the actual adaptation for a specific language or region. Translation is just one piece of localization. The three build on each other, and the strategy for doing this even differs by platform: desktop apps typically ship swappable language packs, the web serves country/language versions that play nicely with browser translation plugins, and mobile apps often ship separate builds with a language switch built in.

Supporting languages isn't the same as designing for them

Swapping in translated strings without tuning anything else produces a specific kind of bad design: broken form layouts for scripts with no punctuation, wrong alignment choices, missing line-height, and English treated as a graphic shape rather than a language with its own logic. The reason is structural. CJK and Latin scripts don't just look different — they run on different grid systems. A Chinese character is a fixed square unit, so the grid is block-based: it controls both line spacing and character spacing, and it aims for a strict, dense rectangle where every line starts and ends on the same vertical line. A Latin grid is baseline-based instead — words vary wildly in length, so alignment happens vertically along a baseline while the horizontal edge is left ragged on purpose. That's also why CJK text typically needs a much taller line-height (1.5–2× the font size, versus roughly 1.2× for Latin) — the visual density of each character just needs more room to breathe. And because CJK has no case distinction to lean on, it builds hierarchy with color blocks, borders, and weight instead of the size-and-whitespace hierarchy Latin typography relies on.

Scripts don't even share a common vertical size at the "same" font size. Latin-like scripts only fill part of their font box; South/Southeast Asian and Middle Eastern scripts (Thai, Hindi, Vietnamese, Arabic) run visibly taller and can get clipped if line-height isn't generous enough; CJK sits in between but reads as visually larger than Latin at equal size, and the gap grows as font size increases — which is why mixed-script UI often needs per-language line-height and a slightly reduced CJK font size to visually match Latin uppercase. Centering text exposes the same divide: English handles a centered, ragged edge well, because varying word lengths, inter-word spacing, and ascender/descender shapes all read as natural rhythm. Chinese has none of that — it's a uniform wall of equal-width characters, so a centered paragraph with a ragged edge reads as broken rather than organic. Centered CJK headlines can still work, but only for short hero-style lines, with a tightly controlled character count, a little extra letter-spacing to lighten the block, and manual correction for the whitespace that full-width punctuation quietly introduces.

Design for expansion, not for the text you started with

Most multilingual bugs are really just a layout that was sized to fit the first language. The practical fix is to treat text length as a variable from the start rather than a fixed constant:

  • Reserve real expansion room in both directions — horizontally so translated strings don't force awkward wraps or truncation, and vertically so line-height accounts for the tallest script in play, not just the one used to design the mockup.
  • Prefer a single stacked column over side-by-side or grid layouts wherever text is long or user-editable — multi-column layouts look efficient in the source language but break first once translated text stops fitting the column width.
  • Be wary of narrow multi-column and tile/grid layouts in general: CJK labels are short enough to fit tight columns, but their translations often aren't, which surfaces as broken words, uneven wrapped-line heights, and mismatched row rhythm. If a grid is unavoidable, widen the columns and reduce the count rather than the reverse.
  • Line-wrap rules aren't universal either — Latin scripts wrap by whole word only, while Japanese has its own rules for where a loanword or punctuation mark may legally break a line. This is a case worth confirming with engineering rather than assuming.
  • When space still runs out, shrink the font size before truncating — and treat ellipsis truncation as a last resort, only acceptable when the meaning survives the cut, and the full text always remains available somewhere else (like a detail page).

The parts that aren't about text at all

Internationalization also touches things that have nothing to do with wording: date and time formats (ISO 8601 versus locale conventions, GMT/UTC versus local time zones), currency and units, name-writing order, font licensing risk when shipping a typeface across regions, and legal frameworks like GDPR that constrain what a product can even collect or display. None of this is exotic — it's just easy to forget because it lives outside the UI copy itself.

A shipping checklist, condensed

The practical process for actually shipping a multilingual product comes down to five steps:

  1. Extract every piece of UI copy — titles, buttons, form labels, dialogs, validation and warning messages — into a numbered source-language pack first.
  2. Build the second language pack, then switch languages and check every string renders correctly, re-checking the first language afterward for any regressions introduced along the way.
  3. Decide on layout up front, not after translation breaks it: favor stacked, left-aligned layouts over centered paragraphs, avoid hard overflow clipping in favor of scrolling, and let multi-column content grow in height together rather than independently.
  4. Expect to need two different content treatments for East Asian versus Western typography — and accept that some assets, like posters with baked-in text, genuinely need to be recut per language rather than reused.
  5. Don't chase perfection. Even a carefully built two-language system can be broken by a user installing a third-party translation plugin that injects an entirely different script. The goal is baseline robustness, not handling every edge case — for interfaces meant to switch across languages, it's sometimes worth trading a bit of visual polish for something that simply holds up.
