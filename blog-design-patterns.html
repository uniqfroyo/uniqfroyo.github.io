Design Patterns

Field notes on what actually holds a design system together — condensed down to the ideas that matter.

This started as a running set of notes on design systems — tokens, governance, tooling, layout, accessibility, and a long catalog of components. Read end to end it's dense, but underneath all of it are really just three questions: what's the smallest unit of truth in a system, who gets to change it, and how do you keep everyone talking about it with the same words.

The token is the atom, not the color

A design token isn't just "a variable for a hex code" — it's a named, three-layer abstraction. A raw value (a specific hex, a specific pixel number) becomes a global token, which gets meaning as a semantic token ("warning color," not "orange-500"), which finally resolves into a component token scoped to one exact use (button-primary-background-hover). Naming a token semantically rather than descriptively is the whole point: it lets the underlying color change without anyone having to rename anything downstream. That same layering shows up again in how a system handles color modes, responsive type scales, and even CSS pseudo-classes — a hover state should reference a token, not hard- code a color, for exactly the same reason.

Governance is a dial, not a decision

Who's allowed to own and change the system is a trade-off, not a best practice. A standalone model (every team runs its own system) maximizes autonomy and speed but fragments into inconsistency. A centralized model (one team owns it, everyone else complies) maximizes consistency but creates a bottleneck. A federated model — several teams contributing under shared rules — tries to sit between the two. None of these is "correct"; the right one depends on how sensitive the organization is to brand consistency versus how many different products it's actually running. The same logic repeats at the structural level, where a system is commonly drawn as a pyramid — foundations, then core components, then community-contributed components, then fully custom UI — each layer trading a little more reusability for a little more flexibility.

Precise language is the real infrastructure

A surprising amount of this document is really about vocabulary, because sloppy vocabulary is where systems quietly break. "Floorplan" and "layout" get treated as synonyms, but they're not: a floorplan is an abstract page archetype (an object page, a wizard, a worklist), while a layout is the concrete, technical arrangement — like a responsive grid — that renders it. "Control" and "component" get confused constantly too: a control (like a checkbox) is a concrete, native interface primitive, while a component is a much fuzzier term that means different things to a designer and an engineer. Even layout itself gets three precise names instead of one — stack for one-dimensional vertical rhythm, cluster for horizontal groups that wrap, grid for genuine two- dimensional structure — because "just use flexbox for everything" eventually produces layouts nobody can reason about.

Complex components are just primitives, recombined

The clearest illustration of system thinking in here isn't a diagram, it's the button family. A button triggers an action. A dropdown button adds one behavior — reveal a menu. A split button separates that same button into two independent hit areas, so one click acts and the other reveals options. A toggle button adds a persistent on/off state. Combine toggle and split and you get a toggle-split button — which looks intimidating until you realize it's just those two already-understood behaviors layered together, not a new concept. That's the actual argument for building a component system out of primitives: once you understand trigger, reveal, and switch, every "new" complex component turns out to be a familiar combination.

Accessibility is a structural constraint, not a pass

The WCAG framework here reduces to four requirements — content must be perceivable, operable, understandable, and robust — and the practical checklist follows directly from them: an icon-only button needs an accessible name because a screen reader can't infer meaning from a shape; focus, selection, and active states all need to be visually distinct because they mean different things (focus is a keyboard position, selection is a data state, active is a momentary press); error and loading states need to be designed up front, not patched in later. None of this is separate from the system — it's the same token-and-state discipline described above, just applied to who can perceive and operate the interface at all.
