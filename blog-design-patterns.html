Design Patterns

Field notes on design tokens, governance, component patterns, and accessibility.

These notes started with a catalog of components and grew to cover tokens, governance, tooling, layout, and accessibility. Three questions kept coming up. What should the system define once and reuse? Who can change it? How do teams keep the terms they use consistent?

How design tokens give raw values meaning

One way to organize design tokens is to use three layers. A global token names a raw value, such as a specific orange or a spacing value. A semantic token names its purpose, such as a warning color. A component token defines how a particular component uses it, as in button-primary-background-hover. A semantic name lets you change the underlying value without changing the names used by components. The same approach applies to color modes, responsive type scales, and states such as hover.

Who should own the design system?

In a standalone model, teams run their own systems. They can move quickly, though patterns may diverge. In a centralized model, one team owns the system, which improves consistency but can slow decisions. A federated model lets multiple teams contribute under shared rules. The right balance depends on how much consistency the organization needs and how much its products differ.

The same trade-off applies to the system’s structure. Foundations and core components are designed for broad reuse. Community contributions and custom UI give teams more room to address specific needs.

Use the same words for the same things

In this system, a floorplan describes a page type, such as a wizard or a worklist. A layout describes how that page is arranged, for example with a responsive grid. A control is an interactive element such as a checkbox. A component is a reusable unit that can contain multiple elements, including controls.

Layout terms can make intent clearer too. A stack arranges items vertically. A cluster groups items in a row that can wrap. A grid aligns items across rows and columns.

Build complex components from familiar behaviors

The button family shows how this works. A standard button triggers an action. A menu button opens a menu. A split button has two targets: one performs the primary action, and the other opens a menu of options. A toggle button keeps an on or off state. A toggle-split button combines that persistent state with the separate menu trigger. Thinking in terms of these behaviors makes it easier to define and document new components.

Build accessibility into the system

The Web Content Accessibility Guidelines (WCAG) organize accessibility around four principles: content should be perceivable, operable, understandable, and robust. In a component library, that means giving icon-only buttons accessible names and making keyboard focus, selection, and a momentary press visually distinct. Define error and loading states early, including how assistive technologies can convey them. Teams can then reuse these decisions wherever the component appears.
